# Testing

**Status: current.** This page describes the suites as they stand after Phase 7, the last phase of [the refactor plan](../implementation/19-refactor.md).

Deckard has one suite per kind of failure. Each catches something no other suite can, so a change is verified by the set, not by one suite.

## The suites

| Script | What it runs | What only it can catch |
| --- | --- | --- |
| `npm run test:unit` | Plain mocha over every suite in `src/test` whose imports never reach `vscode`, as the import graph reads them (`test/harness/runUnitSuites.js`), the files at once in a few worker processes ([below](#unit-suites-at-once)) | Nothing extra. It runs the pure suites in about 16 seconds, so it is the one to run while working. `pretest` runs it first |
| `npm test` | `vscode-test` runs every other suite in an Extension Development Host with `--disable-extensions` and a 20-second timeout | Behavior that needs the real VS Code API: activation, registered commands, settings, editors, and file watchers |
| `npm run test:ui` | `verifyWebviews.js`, then `checkContrast.js` | A page whose script does not parse, a missing design token, a style or script without the page's nonce, a content row without a shared surface in a page's text, a layout rule lost in the cascade, or a zen sheet that is not the last layer |
| `npm run test:contrast` | `checkContrast.js` alone | Text and control contrast below WCAG AA in any theme, including hover, active, and focus states. It resolves tokens from the stylesheet rather than drawing colors, but it asks Chrome which elements each surface draws ([below](#what-the-pages-draw)) |
| `npm run test:e2e` | `test/e2e/run.js`: every `*.e2e.js` in `test/e2e`, found when the run starts, each in its own process, with `vscode` replaced by `vscodeStub.js` and each page mounted in a jsdom window of its own | The real panel host, the real page script, and real messages between them, in one flow |
| `npm run test:layout` | `checkLayout.js` and `checkRenderedContrast.js` in headless Chrome, several pages at once ([below](#drawing-pages-at-once)), with each page's Content-Security-Policy enforced | Geometry: a column that clips its cards, a hover that grows a card past its scroller. Contrast as drawn, with inherited backgrounds, including the icon of a control that has no words, such as the calendar's week mark or the Task Board's move menu, measured where it shows, and the controls `checkRenderedContrast.js` names hovered, such as the sidebar calendar's days, with every `:hover` rule moved onto a class, and text a page holds hidden until it has something to say, such as the Notes Graph's note that it is simulating, shown to be measured. And a page that needs something its policy blocks, since only Chrome enforces CSP. And the rules a page's drawn DOM keeps ([below](#what-the-pages-draw)). Skipped with a message when no Chrome is found, except on CI (`CI` set), where it fails, as does the visual check, which loads it. `CHROME_PATH`, when set, is the only Chrome any of them uses |
| `npm run test:visual` | `checkVisual.js` screenshots a short list of surfaces, 30 of them, and compares pixels to their Linux baselines ([below](#visual-baselines)). On any other system it skips with a message | A backdrop, a glow, or a control that moved. Nothing else sees how a page looks |

`npm run check-types` and `npm run lint` are not suites, but they are the per-commit gate. `check-types` runs `tsc` over the root config and over `src/webview/tsconfig.json`, which checks page code against the DOM. That is what checks the pages' scripts: until Phase 6 step 7, when the last template page was gone, `test:ui` also ran `checkWebviewScripts.js`, which pulled each template page's inline script out by regex and type-checked it with `strict: false`; it is retired and deleted. `lint` runs ESLint over the source (`.ts` and `.tsx`), the tests, and the scripts, and dependency-cruiser over the imports ([layers.md](layers.md)). `bench:index` measures indexing speed and asserts nothing; among its timings is how long the Stats, Task Board, and search page snapshots take to build, which decides whether a page's HTML carries its first snapshot (Q3 in [webviews.md](webviews.md#state)). `LAYOUT_TIMING=1 node test/ui/checkLayout.js` times each surface's first render in Chrome in real time instead of checking its layout, and `scripts/measure-page-bundles.js` uses it, with jsdom and a VSIX, to compare one bundle per page with a shared one ([webviews.md](webviews.md#one-bundle-per-page)).

`compile-tests` builds incrementally, with its build info in `out/.tsbuildinfo`, so a second `test:*` script recompiles only what changed, about 3 seconds rather than 13, and clearing `out/` starts it afresh. Every page links its style sheets from `dist/webview/`, and every page that runs a script loads its bundle from there too, so a suite that draws a page builds them first: `test:unit`, `test:ui`, `test:contrast`, `test:e2e`, `test:layout`, and `test:visual` each run `npm run build:webview` after `compile-tests`, and `pretest` runs `node esbuild.js`, which builds the host and the pages. `node scripts/check-bundle-inputs.js` checks what each bundle took in, from the metafiles the last build wrote to `out/`: the host only the third-party packages it took in when the check arrived, a page's script only Preact, and a page's sheet nothing ([webviews.md](webviews.md#bundling-and-loading)).

## Which suites run where

A suite runs under `test:unit` when none of the modules it imports reaches `vscode`. `test/harness/importGraph.js` reads that from dependency-cruiser each time, and `.vscode-test.mjs` asks it for the rest, so every test runs exactly once and a suite moves to the fast tier as soon as the refactor cuts its last path to `vscode`. After Phase 7, 126 suites run under plain mocha and 95 in the host; [the import-graph inventory](inventories/import-graph.md) says what keeps the rest there.

Those host suites run with no workspace open, so a write to the workspace's or a folder's settings has nowhere to go. The suites in `src/test/scopes/` test where a setting is written and which level's value wins, so `.vscode-test.mjs` runs them twice more, labeled `single-folder` and `multi-root`, each in a workspace it makes empty in the temporary directory at the start of the run. `listHostSuites` lists only `src/test/*.test.ts`, so the run without a workspace never reaches them, and `npx vscode-test --label multi-root` runs one of the three alone. `src/test/scopes/scopes.ts` sets a value at the user, workspace, or folder level as a reader would, and records the context keys Deckard sets.

## The shared harness

The Node harnesses share three modules in `test/harness/`, so a page or a file can move without each harness changing:

| Module | What it does |
| --- | --- |
| `loadPage.js` | Makes a page self-contained: each `<script src>` and stylesheet `<link>` that names a file of the extension is inlined with the page's nonce and marked `data-inlined-from`. A sheet's `url()`s are resolved against the sheet, and the nonce is added to `style-src` for a sheet the policy admits by its origin, so Chrome admits the inline copy exactly when VS Code would admit the link. jsdom runs only inline scripts, Chrome opens a page as an iframe's `srcdoc`, and the text checks read one string, so every harness passes its page through here |
| `modules.js` | Names each compiled module the harnesses load once, as a lazy getter, so a file move is one edit |
| `importGraph.js` | Reads the import graph with the project's own dependency-cruiser configuration |
| `surfacePicks.js` | Picks the surfaces a check draws from its `*_ONLY` variable, and names each by its surface name, since the Task Board's two surfaces share a page. The rendered contrast check uses it |

Tests that assert on CSS text read the sheets as written under `src/webview`, through `src/test/sheets.ts`: `readSheet` and `themeSheet` read one file, `expandSheet` puts each `@import` in place as esbuild does, `linkedSheets` lists the sheets a page's shell links in cascade order, and `pageSheets` and `withSheets` give every rule a page draws with, the latter after its HTML. `verifyWebviews.js` holds the zen sheet, as written, to be the last layer of every loaded page.

`src/test/pages.ts` is the page catalog: every webview page and how to render it. Every mocha suite that builds a page calls its `renderPage(id, options)`, and `test/ui/pages.js` takes its pages from it too, so a builder's signature changes in one file. Each page renders against the one stand-in webview of `src/test/pageWebview.ts`, which names no `vscode` type: its `extensionUri` is the repository, as a stand-in URI a builder joins onto with `with` as it would a `vscode.Uri`, and its `asWebviewUri` hands out every file of the repository as `vscode-webview://deckard/<path>`, the address the page loader reads back. A page that loads its bundle from `dist/webview` therefore runs in every harness, and gets the same URIs on every machine. The e2e stub's `asWebviewUri` maps `dist/webview` the same way. Every Node harness that runs the compiled sources outside VS Code loads that stub with its `install()`, which makes `require('vscode')` resolve to it: the e2e suites and the checks that draw surfaces through `support.js`, and the index bench. `test/ui/pages.js` installs none, since the catalog it renders from reaches no `vscode`. A page builder reads no settings: it is given the theme and zen mode it draws in, as `chrome`, which a host reads as it writes the page and the catalog's `renderPage` takes as an option (Corpo with zen off when a suite names none). So the suites that only render catalog pages run under `test:unit`, and `test/ui/pages.js` passes the theme and zen mode it draws each page in the same way. A host test that hands the extension's folder to VS Code itself makes it with `vscode.Uri.file(REPOSITORY_ROOT)`. `openWebviewPage(html, state, options)` in `src/test/webviewPage.ts` runs a page in jsdom for a mocha suite, and `test/e2e/support.js` mounts one for an e2e suite. Both pass messages as JSON, as VS Code does. `options.savedState` is what the page's `getState` returns from the start, as in a webview VS Code restored. `webview-saved-state.test.ts` uses it to pin what each page draws from every state shape a release has saved (the persisted-formats inventory, rows 20 to 24), and `searchPage.e2e.js` and `taskBoard.e2e.js` pin what the hosts reopen on.

The layout, rendered contrast, and contrast checks draw the surfaces listed in `test/ui/surfaces.js`: a page, the snapshot it is drawn from, and the size it is drawn at. There are 52. Besides the Task Board, the calendars, Related Notes, Stats, and the search page, they cover the Dashboard (Home, Tags, Home being arranged, and Home's search with its builder open), Help, a guide page shown in Help, the Notes Graph's controls, and the Related Notes debug page, and pages with a menu open, so a floating layer at the body's level is drawn too. A surface may name `messages` its host sends after the state, such as Help's guide page; `drive`, the `[event, selector]` pairs a reader's actions dispatch, such as opening a menu; `css` of its own, such as the Notes Graph's, which hides the canvas because its simulation settles differently on each run; and `pageOptions` its page renders with, such as the entry the debug page diagnoses. A driven surface hovers something only its action draws, so the layout check fails if the action stops reaching it. The guide page is a fixture, `test/ui/fixtures/guide-daily-notes.html`, captured in the extension host from `renderGuidePage`, which renders through VS Code's `markdown.api.render`. The debug page runs no script, so its policy names no `script-src`; the harness adds one that admits only its own scripts, by the page's nonce. Its tables wrap their headers, and one still too wide scrolls in its own box, so the page is held to its width like any other.

### Visual baselines

The visual check compares a short list of surfaces, `VISUAL_SET` in `checkVisual.js`: each page's main surface in Mimic, the default theme, and six more of its views, among them the Task Board's lanes and table and its card menu; Home in each of the ten themes; and three with zen on, Cooper's Home among them. It once screenshotted every surface in every theme with zen off and on, over a thousand baselines for each of macOS and Linux, re-recorded on every change to how anything looks; the layout and rendered contrast checks hold every surface in every pass to what can be measured, so the pixels are kept for a few.

The baselines are Linux's alone, in `test/ui/visual-baseline/linux/`, because the operating system rasterizes fonts, and macOS and Linux differ in every glyph's edge. On any other system the check says so and skips. `VISUAL_FORCE=1` compares with the Linux baselines anyway, and `VISUAL_BASELINES=<dir>` compares with, or with `--update` records into, a folder of your own on any system, so a Mac can record the set on one commit and compare on another. Before any Chrome starts, the baselines' names are checked against the set: a baseline the set does not name fails, an entry in the set that names no surface fails, and a surface with no baseline is named and then recorded when drawn, which fails a `--ci` run. Chrome takes each screenshot at a moment it picks, so the harness ends every transition and animation at once and hides the caret: a page is compared where it settles, and an unchanged page draws identically run after run. On macOS alone, Related Notes' native select sometimes draws its chevron flipped, so a darwin-only list in `checkVisual.js` lets `sidebarNotes` and `sidebarNotesUntagged` differ by 0.1% there.

The visual check runs in the Nightly workflow, not on each pull request ([below](#continuous-integration)). When a change in looks is meant, record the new baselines on Linux with `npm run test:visual -- --update`, or run Nightly by hand on the branch with **Only the visual check** ticked: the run fails, and its `visual-changed` artifact holds each image that differed or had no baseline, under its baseline's name, with its diff. Look at them, and commit the ones meant to `test/ui/visual-baseline/linux/`. A surface added to the set is recorded the same way.


The pages' shared core (`src/webview/shared`) is held to the template script it replaced by `src/test/webview-shared.test.ts`: `src/test/sharedBundle.ts` bundles core modules as esbuild builds a page, and the suite draws each component and requires the DOM the template's helper drew, node for node, with the tip, the key sheet, and the undo toast opened as the template opened them. `src/test/webview-tasks.test.ts` does the same for the task row, its title, and its badges; `src/test/webview-query-editor.test.ts` drives the shared search box through the clicks, keys, and typing the template's box was driven through, and requires at each step the DOM it drew, the searches it ran, and focus where it left it; and `src/test/webview-search.test.ts` draws every note excerpt of the sample corpus (`test/fixtures/sample-corpus`, once the Story Tour), the development notes, and the fixtures from its block tokens and through `markdown-it` as the sanitizer left it, and opens the tag menu the template opened. Each compares with `normalizeBody` from `test/harness/domSnapshot.js`, the normalization the contrast check's drawn surfaces and the DOM recorder use. Until step 7 the template's side ran beside the component, from `getComponentScript` and `getQueryEditorScript`. Step 7 deleted those, so the suites first recorded what the template drew, ran, and returned at every comparison into `src/test/fixtures/template/<suite>.json`, which `src/test/templateRecords.ts` reads; a case with no recording fails rather than passing, and the recordings are never rewritten, since the template they record is gone. The task dates in them are local times, so they hold in every time zone, and a floating layer is compared with its neighboring text joined, since its recording is HTML. None of the four reaches `vscode`, so they run under `test:unit`: `webview-search.test.ts` reads the sample corpus through `src/test/indexCorpus.ts`, which takes the date tokens and file names from `src/domain/notes/sampleNotes.ts`, as the Work Sample's command does. Since step 6 removed `sanitize-html`, the excerpts and titles take the template's HTML from `src/test/legacyMarkdown.ts`, `markdown-it` with its renderer writing what the sanitizer kept, which agreed with `rendering.ts` on every excerpt and title the suites draw before that file went. It needs no `@testing-library/preact`, and `openWebviewPage` stays the page harness. Catalog pages that read their first snapshot from the shell say so with `readsInertState`, and `renderPage(id, { state })` builds the shell with it, so a suite can draw a page both ways.

### What the pages draw

A compiled page leaves no markup to read as text, so the checks that ask what a page draws ask Chrome, at check time, and keep nothing. They once read DOM goldens, `test/ui/dom-baseline/`, a normalized body for every surface with zen off and on that `test:dom` compared, which a harmless change to an attribute rewrote by the dozen; they are retired.

The contrast check's element shapes are the union of `test/ui/contrast-shapes.json` and the shapes each surface draws. The file holds the shapes the check read from each page's text before Phase 6, frozen with every attribute a rule asks about so states no surface draws stay in the matrix; it is an input, never rewritten by a run. The drawn shapes come from `test/ui/drawnSurfaces.js`, which draws every surface as the layout check draws it, in Replicant with zen off and on, since the theme changes no markup but the gear's theme name and zen draws a few elements otherwise, and hands back each body in memory, captured by the layout probe before it touches anything and normalized by `test/harness/domSnapshot.js`: scripts, style sheets, and comments dropped, attributes and classes sorted, and a form control's value, checkedness, and selectedness carried as `data-dom-*`. On the commit that retired the goldens, every body it drew was byte for byte the golden it replaced. That is 104 pages, some 4 to 5 minutes with two Chromes; without Chrome the check judges the frozen shapes alone and says so, except on CI, where it fails. The drawn shapes found the calendar's day and week buttons, which the text could not name; both are written `background: none`, which the model once read as no background declared, handing them the theme's button fill, and reads now as transparent, as the browser does, so `contrast-baseline.json` is empty. The model reads no icon and settles a hovered element's color by its state before its specificity, so the calendar's icons and a hovered day outside the month are left to the rendered check.

The layout check captures each surface's body the same way, in every pass, and holds it to the rules in `test/ui/drawnDomRules.js`: every content row carries a shared surface, no control or element with a tabindex carries a native title, a page fills at most one control and only one that commits something, and a card that shows more of itself on hover says so to the tip with `data-tip-around`. A run that draws every surface and finds too few filled controls or opening cards fails, since its rules would be reading nothing. `verifyWebviews.js` holds the page text to the content-row rule as well, which still holds the body of a page whose host builds it (Help and the debug page), and does not parse or nonce-check a page's `application/json` state; the "no native title" unit test reads the page text, and an ESLint rule forbids `title` on a control or an element with `tabIndex` in `.tsx`, for the states no surface draws. A page that reads its first snapshot from its shell must draw the same DOM as when the snapshot is posted; `components-primitives.test.ts` draws each such page both ways in jsdom and compares the normalized bodies.

The page-driving suites can record every state they reach, for the states no surface draws: an open menu, a builder row, a column removed. With `DECKARD_DOM_RECORD=<dir>`, `openWebviewPage` writes the page's normalized body after each `send` and `click`, and `test/e2e/support.js` after each message the host delivers and each reader action, keyed by suite file, mount, and step (`test/harness/domRecorder.js`). Run the suites on the phase base and on a branch, each into its own folder, then `node test/ui/diffDomRecords.js <base> <branch>` lists every state that differs. A few states draw the wall clock, such as Stats' last refresh, so a second base run passed as a third folder sets aside the states that differ from run to run. The records are not committed. `openWebviewPage`'s `clockStep` option makes `performance.now()` move on a fixed amount per reading, so a page that animates by the clock, such as the Notes Graph, draws the same frames every run. Its `clock` option gives the page a clock the test moves by hand (`src/test/manualClock.ts`): the window's timers and `Date.now` wait until `page.clock.advance(ms)`, which runs every timer due by then in the order each fell due, so a test of a 400 ms pause takes no 400 ms and can pin the pause to the millisecond. `installManualClock(globalThis)` does the same for code that runs in Node, such as the debouncers. Each timer path keeps one test on the real clock, so a bug only real timers show still fails somewhere.

### Drawing pages at once

The layout and rendered-contrast checks each open a headless Chrome for every surface in every pass, 1,040 pages a check; the contrast check opens 104 and the visual check 30. When the checks drew a third as many pages, opened one at a time, `test:layout` took 24 minutes and `test:visual` 19 on a 16-thread Mac. They now draw through a small pool, `test/ui/chromePool.js`: `UI_CONCURRENCY=<n>` Chromes at once, or, unset, half the machine's logical cores, at least one and at most four. `UI_CONCURRENCY=1` draws one page at a time, as the checks always did. Each Chrome gets a profile of its own under the temporary folder, incognito, since a headless Chrome with a profile on disk writes the page out and then never exits, and runs in a process group of its own, so a wedged Chrome is killed with its helpers and a check never kills a Chrome it did not start. A wedge is still retried once per page, then fails that surface with the same message. What each page prints is held until every page before it has printed, so a run reports the same surfaces, in the same order, with the same lines and summary, as a run one at a time. Files are named by pass and surface, so no two pages share one.

A Chrome costs some five seconds of CPU to start, draw one page, and quit, so the pool runs out of cores before it runs out of pages: on that Mac, four at once drew 48 pages in 55 seconds against 86 one at a time, and eight in 51, no faster. Time in each Chrome is virtual, and it runs on while Chrome loads the page's frame, so the busier the machine, the later in virtual time a page finishes: its probe, written about 0.25 seconds in when one page is drawn at a time, came as late as 2.3 seconds of the 3-second budget with eight at once, and 0.7 with four. That is why the default stops at four, and why the page the layout and contrast checks build no longer reads the probe at a fixed 0.4 seconds but waits for it. Measured on that Mac on one afternoon, the unchanged checks took 20.8 minutes for layout and rendered contrast and 11.2 for the visual check, one page at a time; with four at once, `npm run test:layout` took 12.3 minutes and `npm run test:visual` 6.9, the build each runs first included, and every surface had the same verdict. A wedged Chrome now holds up one of the four rather than the whole run. `LAYOUT_TIMING=1` still draws one page at a time.

### Shards

`UI_SHARD=<k>/<n>` makes the layout, rendered-contrast, and visual checks take every n-th of the twenty passes, starting with the k-th (`test/ui/passes.js`), so the shards of one n make every pass exactly once; CI runs the layout and rendered contrast checks in two each. The matrix is split, never sampled: 162a7c7c failed only in Corpo with zen. `VISUAL_CHANGED=<dir>` makes the visual check copy there only what a failure needs: each image drawn with no baseline or differing from it, under its baseline's name, and its diff.

### Unit suites at once

`test:unit` runs each suite file in one of a few worker processes (mocha's parallel mode): one fewer than the logical cores, at least two, at most four on CI and eight elsewhere, or `UNIT_JOBS=<n>`. On a 16-thread Mac the 162 files took 50 seconds one after another and 16 at once. `UNIT_SERIAL=1` runs them in one process, one after another, as the nightly run does, so a suite that leans on what another file left behind, or on the order files run in, still shows. On CI (`CI` set) a `.only` left in a suite fails the unit, host, and end-to-end runs rather than running one test and passing.

## When to run what

| When | Run |
| --- | --- |
| Every commit | `npm run check-types && npm run lint` |
| While changing pure logic | `npm run test:unit` |
| After changing shared webview components or a page | `npm run test:ui` |
| When the change touches a scroll container, a column, or a hover | `npm run test:layout` |
| When the change touches how anything looks | `npm run test:visual` on Linux, or Nightly's visual check by hand ([Visual baselines](#visual-baselines)) |
| Once before a branch lands | `npm test`, `test:ui`, `test:e2e`, and `test:layout`, gated on their exit codes; CI runs them all, and Nightly the visual check |

A refactor phase lands only on a clean full run with no pixel changes. A visual diff during a refactor means behavior changed, which is a bug in the refactor.

## Continuous integration

`ci.yml` runs once for each commit: on every pull request, and, through `workflow_call`, as the first job of a release. A push runs nothing of its own; a branch that wants CI opens a pull request, a draft if it is not ready, or runs the workflow by hand. Its work is split between jobs that run at once, so a run takes as long as its slowest job, about 6 to 8 minutes where the one job it replaced took 18 to 27:

| Job | What it runs |
| --- | --- |
| `checks` | `npm audit --omit=dev --audit-level=high`, so a package the extension ships cannot carry a high or critical advisory; `check-types`; `lint`, with dependency-cruiser; and the folder-level import graph, written to the run's summary. A type error shows in about a minute |
| `core` | One build, `compile-tests` and `node esbuild.js`, then the unit suites, the three host labels under `xvfb`, `verifyWebviews.js`, the end-to-end suites, and the VSIX, packaged without a second lint (`DECKARD_LINTED=1`), then `scripts/check-bundle-inputs.js` over its production build |
| `browser` | Five jobs: layout and rendered contrast, each in two shards ([Shards](#shards)), and `checkContrast.js`, which asks Chrome what the surfaces draw. Each draws two pages at a time on the runner's four cores ([Drawing pages at once](#drawing-pages-at-once)) |
| `extension-host` | The unit suites and the three host labels on `windows-latest` and `macos-latest`, for what Linux cannot show: drive letters, backslashes, and line endings. Lint reads the same files on every system, so it runs in `checks` alone; the pages are drawn and compared on Linux only |
| `validate` | Waits for every other job and fails unless each succeeded. Master's ruleset requires this check by name. A job whose needs failed is skipped, and a skipped required check counts as passing, so it runs `if: always()` |

The Chrome checks draw in a pinned Chrome, `CHROME_VERSION` in `ci.yml` and `nightly.yml`: Chrome for Testing, installed by `browser-actions/setup-chrome` and passed as `CHROME_PATH`, at the version the Linux baselines were drawn in, since the runner's own Chrome moves with each image. Raise it in both in the commit that re-records the Linux baselines. The host suites run in a pinned VS Code, `VSCODE_VERSION`, which `.vscode-test.mjs` reads (today's stable when unset), and its download is cached by system and version. Dependabot (`.github/dependabot.yml`) opens the updates, to `dev`, for every package and every action.

`nightly.yml` runs the same set on `dev` each night, and by hand on any branch, the slow way: one Linux job with the unit suites in one process (`UNIT_SERIAL=1`) and each Chrome check over all twenty passes, the unit and host suites on Windows and macOS, and the host suites in VS Code 1.134.0, the oldest `engines` allows, where CI runs a recent one. It catches what the split run can hide: a suite that leans on another file's state or on the order files run in, a test that fails only on a later date, and an API newer than `engines` promises. A job of its own runs the visual check with `--ci`, so a surface with no baseline fails rather than being recorded, and a failed run uploads as its `visual-changed` artifact only the images that differ or had none, under their baselines' names, and their diffs. Run by hand with **Only the visual check** ticked, it runs that job alone, which is how Linux baselines are taken ([Visual baselines](#visual-baselines)). A scheduled workflow runs from master's copy of the file.

`prepare-release.yml` cuts a release, the version and the changelog's section, when the pull request from `dev` is given the `release` label, or when run by hand on `dev`, not on every push, since each cut commit starts a full CI run of its own.

`release.yml` calls the whole workflow as a reusable workflow before it builds and publishes, so a merge whose CI run was cancelled is not released untested. Then it runs three jobs, each with only the permissions it needs: `build` packages the VSIX once and signs its provenance (`gh attestation verify <vsix> --repo doctorallen/deckard` checks it); `github-release` creates the release with that file; `marketplace` publishes the same file from the `marketplace` environment, which only master may deploy to and which the Microsoft Entra credential trusts. Every action is pinned to a full commit SHA, with its version in a comment, and `codeql.yml` scans the code and the workflows on each pull request, after each merge, and weekly.

A page's host-controller tests run its `PageController` in a `WebviewHost` attached to the `FakeSurface` of `src/test/fakeWebview.ts`, around a `FakeWebview` that has only `postMessage` and `onDidReceiveMessage`. A test sends what the page would with `await surface.webview.send(message)`, which resolves when the handler has finished, and reads what the host posted in `surface.webview.posted`. `stats-host.test.ts` is the first; [webviews.md](webviews.md#moving-a-host-onto-webviewhost) says how each page adds its own. `navigation.e2e.js` pins, against the hosts themselves, which lines and tags each page's `openSource` and `openTag` open, so a host moved onto the shared handlers is held to what it accepted before.
