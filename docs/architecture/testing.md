# Testing

**Status: current.** This page describes the suites as they stand after Phase 7, the last phase of [the refactor plan](../implementation/19-refactor.md).

Deckard has one suite per kind of failure. Each catches something no other suite can, so a change is verified by the set, not by one suite.

## The suites

| Script | What it runs | What only it can catch |
| --- | --- | --- |
| `npm run test:unit` | Plain mocha over every suite in `src/test` whose imports never reach `vscode`, as the import graph reads them (`test/harness/runUnitSuites.js`) | Nothing extra. It runs the pure suites in a fraction of a second, so it is the one to run while working. `pretest` runs it first |
| `npm test` | `vscode-test` runs every other suite in an Extension Development Host with `--disable-extensions` and a 20-second timeout | Behavior that needs the real VS Code API: activation, registered commands, settings, editors, and file watchers |
| `npm run test:ui` | `verifyWebviews.js`, then `checkContrast.js` | A page whose script does not parse, a missing design token, a style or script without the page's nonce, a content row without a shared surface, a layout rule lost in the cascade, or a zen sheet that is not the last layer |
| `npm run test:contrast` | `checkContrast.js` alone | Text and control contrast below WCAG AA in any theme, including hover, active, and focus states. It resolves tokens from the stylesheet rather than drawing |
| `npm run test:e2e` | `test/e2e/run.js`: nine mocha suites, each in its own process, with `vscode` replaced by `vscodeStub.js` and each page mounted in a jsdom window of its own | The real panel host, the real page script, and real messages between them, in one flow |
| `npm run test:layout` | `checkLayout.js` and `checkRenderedContrast.js` in headless Chrome, with each page's Content-Security-Policy enforced | Geometry: a column that clips its cards, a hover that grows a card past its scroller. Contrast as drawn, with inherited backgrounds. And a page that needs something its policy blocks, since only Chrome enforces CSP. Skipped with a message when no Chrome is found |
| `npm run test:visual` | `checkVisual.js` screenshots every surface, theme, and zen state, and compares pixels to a baseline | A backdrop, a glow, or a control that moved. Nothing else sees how a page looks |
| `npm run test:dom` | `checkDom.js` draws every surface in Chrome, in Replicant with and without zen, and compares its normalized body with the golden in `test/ui/dom-baseline/`. A surface of a page that reads its first snapshot from its shell is drawn twice, posted and embedded, and the two must match | A class, attribute, element, or text node that changed anywhere on a page, before any pixel moves and below the first screen. It is the gate for Phase 6, which rewrites every page's markup |

`npm run check-types` and `npm run lint` are not suites, but they are the per-commit gate. `check-types` runs `tsc` over the root config and over `src/webview/tsconfig.json`, which checks page code against the DOM. That is what checks the pages' scripts: until Phase 6 step 7, when the last template page was gone, `test:ui` also ran `checkWebviewScripts.js`, which pulled each template page's inline script out by regex and type-checked it with `strict: false`; it is retired and deleted. `lint` runs ESLint over the source (`.ts` and `.tsx`), the tests, and the scripts, and dependency-cruiser over the imports ([layers.md](layers.md)). `bench:index` measures indexing speed and asserts nothing; among its timings is how long the Stats, Task Board, and search page snapshots take to build, which decides whether a page's HTML carries its first snapshot (Q3 in [webviews.md](webviews.md#state)). `LAYOUT_TIMING=1 node test/ui/checkLayout.js` times each surface's first render in Chrome in real time instead of checking its layout, and `scripts/measure-page-bundles.js` uses it, with jsdom and a VSIX, to compare one bundle per page with a shared one ([webviews.md](webviews.md#one-bundle-per-page)).

Every page links its style sheets from `dist/webview/`, and every page that runs a script loads its bundle from there too, so a suite that draws a page builds them first: `test:unit`, `test:ui`, `test:contrast`, `test:e2e`, `test:layout`, `test:visual`, and `test:dom` each run `npm run build:webview` after `compile-tests`, and `pretest` runs `node esbuild.js`, which builds the host and the pages. `node scripts/check-bundle-inputs.js` checks what each bundle took in, from the metafiles the last build wrote to `out/`: the host only the third-party packages it took in when the check arrived, a page's script only Preact, and a page's sheet nothing ([webviews.md](webviews.md#bundling-and-loading)).

## Which suites run where

A suite runs under `test:unit` when none of the modules it imports reaches `vscode`. `test/harness/importGraph.js` reads that from dependency-cruiser each time, and `.vscode-test.mjs` asks it for the rest, so every test runs exactly once and a suite moves to the fast tier as soon as the refactor cuts its last path to `vscode`. After Phase 7, 126 suites run under plain mocha and 95 in the host; [the import-graph inventory](inventories/import-graph.md) says what keeps the rest there.

Those host suites run with no workspace open, so a write to the workspace's or a folder's settings has nowhere to go. The suites in `src/test/scopes/` test where a setting is written and which level's value wins, so `.vscode-test.mjs` runs them twice more, labeled `single-folder` and `multi-root`, each in a workspace it makes empty in the temporary directory at the start of the run. `listHostSuites` lists only `src/test/*.test.ts`, so the run without a workspace never reaches them, and `npx vscode-test --label multi-root` runs one of the three alone. `src/test/scopes/scopes.ts` sets a value at the user, workspace, or folder level as a reader would, and records the context keys Deckard sets.

## The shared harness

The Node harnesses share three modules in `test/harness/`, so a page or a file can move without each harness changing:

| Module | What it does |
| --- | --- |
| `loadPage.js` | Makes a page self-contained: each `<script src>` and stylesheet `<link>` that names a file of the extension is inlined with the page's nonce and marked `data-inlined-from`. A sheet's `url()`s are resolved against the sheet, and the nonce is added to `style-src` for a sheet the policy admits by its origin, so Chrome admits the inline copy exactly when VS Code would admit the link. jsdom runs only inline scripts, Chrome opens a page as an iframe's `srcdoc`, and the text checks read one string, so every harness passes its page through here |
| `modules.js` | Names each compiled module the harnesses load once, as a lazy getter, so a file move is one edit |
| `importGraph.js` | Reads the import graph with the project's own dependency-cruiser configuration |
| `surfacePicks.js` | Picks the surfaces a check draws from its `*_ONLY` variable, and names each by its surface name, since the Task Board's two surfaces share a page. The rendered contrast check uses it |

Tests that assert on CSS text read the sheets as written under `src/webview`, through `src/test/sheets.ts`: `readSheet` and `themeSheet` read one file, `expandSheet` puts each `@import` in place as esbuild does, `linkedSheets` lists the sheets a page's shell links in cascade order, and `pageSheets` and `withSheets` give every rule a page draws with, the latter after its HTML. `verifyWebviews.js` holds the zen sheet, as written, to be the last layer of every loaded page.

`src/test/pages.ts` is the page catalog: every webview page and how to render it. Every mocha suite that builds a page calls its `renderPage(id, options)`, and `test/ui/pages.js` takes its pages from it too, so a builder's signature changes in one file. Each page renders against the one stand-in webview of `src/test/pageWebview.ts`, which names no `vscode` type: its `extensionUri` is the repository, as a stand-in URI a builder joins onto with `with` as it would a `vscode.Uri`, and its `asWebviewUri` hands out every file of the repository as `vscode-webview://deckard/<path>`, the address the page loader reads back. A page that loads its bundle from `dist/webview` therefore runs in every harness, and gets the same URIs on every machine. The e2e stub's `asWebviewUri` maps `dist/webview` the same way. Every Node harness that runs the compiled sources outside VS Code loads that stub with its `install()`, which makes `require('vscode')` resolve to it: the e2e suites and the checks that draw surfaces through `support.js`, and the index bench. `test/ui/pages.js` installs none, since the catalog it renders from reaches no `vscode`. A page builder reads no settings: it is given the theme and zen mode it draws in, as `chrome`, which a host reads as it writes the page and the catalog's `renderPage` takes as an option (Corpo with zen off when a suite names none). So the suites that only render catalog pages run under `test:unit`, and `test/ui/pages.js` passes the theme and zen mode it draws each page in the same way. A host test that hands the extension's folder to VS Code itself makes it with `vscode.Uri.file(REPOSITORY_ROOT)`. `openWebviewPage(html, state, options)` in `src/test/webviewPage.ts` runs a page in jsdom for a mocha suite, and `test/e2e/support.js` mounts one for an e2e suite. Both pass messages as JSON, as VS Code does. `options.savedState` is what the page's `getState` returns from the start, as in a webview VS Code restored. `webview-saved-state.test.ts` uses it to pin what each page draws from every state shape a release has saved (the persisted-formats inventory, rows 20 to 24), and `searchPage.e2e.js` and `taskBoard.e2e.js` pin what the hosts reopen on.

Visual baselines are kept per platform in `test/ui/visual-baseline/<platform>/`, because the operating system rasterizes fonts, and macOS and Linux differ in every glyph's edge. Chrome takes each screenshot at a moment it picks, so the harness ends every transition and animation at once and hides the caret: a page is compared where it settles, and an unchanged page draws identically run after run. The one exception is Synthwave's Task Board, by status, by tag, and with a card's menu open, whose columns still come to rest a strip of a card apart now and then, about 0.04% of the page; `checkVisual.js` names those three surfaces and lets them differ by 0.1% of the page rather than 0.01% until that is fixed. On macOS alone, Related Notes' native select sometimes draws its chevron flipped, which no darwin baseline can settle, so a darwin-only list in `checkVisual.js` lets `sidebarNotes` and `sidebarNotesUntagged` differ by 0.1% there; Linux, the gate of record, never reads it. When a change in looks is meant, record it with `npm run test:visual -- --update` and commit the new baselines.

The layout, visual, and DOM checks draw the same surfaces, listed in `test/ui/surfaces.js`: a page, the snapshot it is drawn from, and the size it is drawn at. There are 21. Besides the Task Board, the calendars, Related Notes, Stats, and the search page, they cover the Dashboard (Home, Tags, Home being arranged, and Home's search with its builder open), Help, a guide page shown in Help, the Notes Graph's controls, and the Related Notes debug page, and two pages with a menu open, so a floating layer at the body's level is drawn too. A surface may name `messages` its host sends after the state, such as Help's guide page; `drive`, the `[event, selector]` pairs a reader's actions dispatch, such as opening a menu; `css` of its own, such as the Notes Graph's, which hides the canvas because its simulation settles differently on each run; and `pageOptions` its page renders with, such as the entry the debug page diagnoses. A driven surface hovers something only its action draws, so the layout check fails if the action stops reaching it. The guide page is a fixture, `test/ui/fixtures/guide-daily-notes.html`, captured in the extension host from `renderGuidePage`, which renders through VS Code's `markdown.api.render`. The debug page runs no script, so its policy names no `script-src`; the harness adds one that admits only its own scripts, by the page's nonce. Its tables are as wide as their evidence, so its width is not measured. Fellowship's Notes Graph status line is below AA as drawn (4.43:1); `checkRenderedContrast.js` lists it as known rather than fixing it during the refactor.

The pages' shared core (`src/webview/shared`) is held to the template script it replaced by `src/test/webview-shared.test.ts`: `src/test/sharedBundle.ts` bundles core modules as esbuild builds a page, and the suite draws each component and requires the DOM the template's helper drew, node for node, with the tip, the key sheet, and the undo toast opened as the template opened them. `src/test/webview-tasks.test.ts` does the same for the task row, its title, and its badges; `src/test/webview-query-editor.test.ts` drives the shared search box through the clicks, keys, and typing the template's box was driven through, and requires at each step the DOM it drew, the searches it ran, and focus where it left it; and `src/test/webview-search.test.ts` draws every note excerpt of the sample workspace, the development notes, and the fixtures from its block tokens and through `markdown-it` as the sanitizer left it, and opens the tag menu the template opened. Each compares with `normalizeBody` from `test/harness/domSnapshot.js`, the normalization `test:dom` uses. Until step 7 the template's side ran beside the component, from `getComponentScript` and `getQueryEditorScript`. Step 7 deleted those, so the suites first recorded what the template drew, ran, and returned at every comparison into `src/test/fixtures/template/<suite>.json`, which `src/test/templateRecords.ts` reads; a case with no recording fails rather than passing, and the recordings are never rewritten, since the template they record is gone. The task dates in them are local times, so they hold in every time zone, and a floating layer is compared with its neighboring text joined, since its recording is HTML. The first three no longer reach `vscode`, so they run under `test:unit`; `webview-search.test.ts` still runs in the host, because it reads the sample workspace through `src/ui/commands/sampleWorkspace.ts`. Since step 6 removed `sanitize-html`, the excerpts and titles take the template's HTML from `src/test/legacyMarkdown.ts`, `markdown-it` with its renderer writing what the sanitizer kept, which agreed with `rendering.ts` on every excerpt and title the suites draw before that file went. It needs no `@testing-library/preact`, and `openWebviewPage` stays the page harness. Catalog pages that read their first snapshot from the shell say so with `readsInertState`, and `renderPage(id, { state })` builds the shell with it, so a suite can draw a page both ways.

The DOM goldens in `test/ui/dom-baseline/<surface>[+zen].html` were recorded from the pages before Phase 6 rewrote any markup, and are re-recorded (`npm run test:dom -- --update`) only by a commit that names the difference it accepts. The layout check's probe clones the body before it measures anything, and `test/harness/domSnapshot.js` normalizes the clone, so a golden holds only what a selector or a reader could tell apart. Scripts, style sheets, comments, and the probe's output are dropped, and the nonce reads `NONCE`. Attributes and class names are sorted, a boolean attribute is written as `""`, and a style attribute is written from its declarations, sorted. A form control's value, checkedness, and selectedness are read from the control and carried as `data-dom-*`, since a component sets properties where a template wrote attributes. Text is merged and its whitespace collapsed, but a text node of only whitespace is kept, and a difference of spacing alone fails as one, because a space between two inline elements is visible. The golden is HTML that parses back to the normalized body, with a line break inside each tag, so a diff reads line by line. The DOM is Chrome's, laid out at each surface's size, because the Task Board draws only the cards on screen; the goldens are recorded on macOS, and `test:dom` is not run on CI.

Three checks used to find elements by reading markup out of the page scripts' string literals, which compiled TSX does not have. Each now reads the drawn DOM as well, through `test/harness/domGoldens.js`, which parses the goldens; `test:dom` keeps the goldens equal to what the pages draw. The contrast check's element shapes are the union of `test/ui/contrast-shapes.json`, the shapes it read from each page's text before Phase 6, frozen with every attribute a rule asks about so states no surface draws stay in the matrix, and the shapes each surface draws. The drawn shapes found the calendar's day and week buttons, which the text could not name; their findings are in `contrast-baseline.json`. `verifyWebviews.js` holds content rows to a shared surface in both the page text, which still holds the body of a page whose host builds it (Help and the debug page), and the drawn DOM, and does not parse or nonce-check a page's `application/json` state. The "no native title" test reads both, and an ESLint rule forbids `title` on a control or an element with `tabIndex` in `.tsx`, for the states no surface draws. The drawn DOM found one it could not read before, the Notes Graph's tag filter checkboxes, which the test names as known. The "starts busy" test reads the loaded page's DOM.

The page-driving suites can record every state they reach, for the states no surface draws: an open menu, a builder row, a column removed. With `DECKARD_DOM_RECORD=<dir>`, `openWebviewPage` writes the page's normalized body after each `send` and `click`, and `test/e2e/support.js` after each message the host delivers and each reader action, keyed by suite file, mount, and step (`test/harness/domRecorder.js`). Run the suites on the phase base and on a branch, each into its own folder, then `node test/ui/diffDomRecords.js <base> <branch>` lists every state that differs. A few states draw the wall clock, such as Stats' last refresh, so a second base run passed as a third folder sets aside the states that differ from run to run. The records are not committed. `openWebviewPage`'s `clockStep` option makes `performance.now()` move on a fixed amount per reading, so a page that animates by the clock, such as the Notes Graph, draws the same frames every run.

## When to run what

| When | Run |
| --- | --- |
| Every commit | `npm run check-types && npm run lint` |
| While changing pure logic | `npm run test:unit` |
| After changing shared webview components or a page | `npm run test:ui` |
| When the change touches a scroll container, a column, or a hover | `npm run test:layout` |
| When the change touches how anything looks | `npm run test:visual` |
| While rewriting a page's markup (Phase 6) | `npm run test:dom` |
| Once before a branch lands | `npm test`, `test:ui`, `test:e2e`, `test:layout`, `test:visual`, and `test:dom`, gated on their exit codes |

A refactor phase lands only on a clean full run with no pixel changes. A visual diff during a refactor means behavior changed, which is a bug in the refactor.

## Continuous integration

`ci.yml` runs on pushes to `dev`, the release branches, and every `refactor/**` branch, and on pull requests into the release branches, with a 25-minute limit. It runs `npm test` under `xvfb`, which runs `test:unit` first, then `test:ui`, `test:e2e`, `test:layout`, and `test:visual -- --ci`. After packaging the VSIX it runs `scripts/check-bundle-inputs.js` over the production build. With `--ci`, a surface with no baseline fails the run rather than being recorded, and the screenshots, diffs, and any recorded baseline are uploaded as the run's `visual-<sha>` artifact. Each run also writes the folder-level import graph to its summary.

`release.yml` calls the same job as a reusable workflow before it builds and publishes, so a merge whose CI run was cancelled is not released untested.

A page's host-controller tests run its `PageController` in a `WebviewHost` attached to the `FakeSurface` of `src/test/fakeWebview.ts`, around a `FakeWebview` that has only `postMessage` and `onDidReceiveMessage`. A test sends what the page would with `await surface.webview.send(message)`, which resolves when the handler has finished, and reads what the host posted in `surface.webview.posted`. `stats-host.test.ts` is the first; [webviews.md](webviews.md#moving-a-host-onto-webviewhost) says how each page adds its own. `navigation.e2e.js` pins, against the hosts themselves, which lines and tags each page's `openSource` and `openTag` open, so a host moved onto the shared handlers is held to what it accepted before.
